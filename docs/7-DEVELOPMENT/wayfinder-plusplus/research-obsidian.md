## 2. Protocol options (primary sources)

### Option A — Plain filesystem access (recommended for first slice)
- An Obsidian vault **is a folder of Markdown files + attachments + subfolders on the local filesystem**; Obsidian creates a hidden `.obsidian` config folder (settings, themes, plugins, workspace state) inside the vault root — content is the notes/attachments, `.obsidian` is app state, not knowledge. Source: https://help.obsidian.md/data-storage and https://raccoon.page/blog/export-obsidian-vault (summarizing the same structure).
- Internal links are vault-relative and come in two interchangeable formats: Wikilink `[[name]]` (Obsidian default, compact) and standard Markdown `[text](path)` (portable); setting "Use Wikilinks" off makes Obsidian emit Markdown links. Renames auto-update links inside Obsidian. Source: https://obsidian.md/help/links
- Attachments land per `Settings → Files and links → Default location for new attachments` (vault folder, subfolder, or next-to-note). Any external writer that drops files must expect arbitrary attachment dirs. Source: Obsidian attachment settings (e.g. https://www.obsidianstats.com/plugins/attachment-management documents the same setting surface).
- Implication: a **read-only bind mount** (`<vault>:/app/vault:ro`) + file watcher posting to `POST /sources` needs zero Obsidian cooperation and cannot corrupt the vault. This is exactly `local-open-notebook.md` Tasks 4–5.

### Option B — Official `obsidian://` URI scheme (open/search/new; no bulk API)
- Official custom protocol; actions: `open` (open vault/note via `vault=` + `file=` vault-relative path, or absolute `path=` which overrides both and auto-selects the containing vault), `new` (create note via `name=` honoring "default location" or `file=` vault-absolute path, optional `content=`), `daily` (open/create daily note), `unique` (timestamped note), `search` (open Search + optional query), `choose-vault`; shorthand `obsidian://vault/<vault>/<note>` ≡ `open?vault&file`. Sources: https://help.obsidian.md/Obsidian+URI , https://help.obsidian.md/Extending+Obsidian/Obsidian+URI , https://help.obsidian.md/Advanced+topics/Using+Obsidian+URI (same page, multiple paths).
- Use for: "open this exported note in Obsidian" deep-links and capture/append helpers. Not a sync transport: one action per URI invocation, requires Obsidian running, no listing/read-all, no auth model, no change events.

### Option C — Community Local REST API plugin (full CRUD + search + events, when Obsidian runs)
- Plugin `coddingtonbear/obsidian-local-rest-api` (~3k stars) exposes HTTPS `https://127.0.0.1:27124` (Bearer API key, self-signed CA) plus optional plain-HTTP `:27123` and a built-in MCP server at `/mcp/`. Source: https://github.com/coddingtonbear/obsidian-local-rest-api and interactive docs https://coddingtonbear.github.io/obsidian-local-rest-api/
- Endpoint surface (same page): `/vault/{path}` GET/PUT/PATCH/POST/DELETE (any vault file, incl. binary bodies), `/active/` (currently open file), `/search/simple/` (fuzzy full-text) and `/search/` (JsonLogic over frontmatter/tags/path/content), `/commands/` + `/commands/{id}` (list/execute palette commands), `/tags/`, `/open/{path}` (open in UI), `/` (status/auth/state), `/mcp/`.
- Notable for sync design: surgical `PATCH` (target heading/block/frontmatter key × operation append/prepend/replace/delete/move, `ifMatch` optimistic concurrency via document-map `version`), URL-embedded section targeting (`/vault/note.md/heading/My%20Section`, `/frontmatter/<key>`), SSE event streams (`vault` create/modify/delete/rename, `metadataCache` changed/deleted/resolve/resolved, `workspace` file-open…), and `.obsidian` config dir **blocked by default** (403) since it holds plugin code/secrets. Source: same README sections "Patching notes", "Targeting specific sections", "Event streams", "The configuration directory is off-limits".
- Alternative plugin `rest-api` v0.1.0 (community page https://community.obsidian.md/plugins/rest-api) offers similar CRUD + periodic-notes/Dataview-DQL endpoints, but single release and smaller adoption — keep as backup, standardize on `coddingtonbear` if a plugin route is chosen.
- Caveat for Docker: plugin binds to the desktop host's loopback; the `open_notebook` container reaches it only via `host.docker.internal` + user-enabled HTTP/plain port or trusted CA, and only while Obsidian is running — strictly weaker availability than a filesystem mount for the always-on local stack.

### Option D — Vault markdown + frontmatter conventions (what both directions must emit/parse)
- Notes are Markdown; structured metadata lives in a YAML frontmatter block (`---` fences) at the very top, edited via the Properties panel (two views of the same data). Source: https://obsidian.md/help/properties and https://obsidianmate.com/article/obsidian-properties-complete-guide
- Property types: Text, List, Number, Checkbox, Date, Date & time (six), plus defaults `tags`, `aliases` (`cssclasses`); type is per-property-name vault-wide (managed in All Properties / `.obsidian/types.json`); old singular keys `tag`/`alias`/`cssclass` deprecated in favor of plural list forms. Sources: https://obsidian.md/help/properties , https://www.kevsrobots.com/learn/obsidian/09_properties.html , forum deprecation note https://forum.obsidian.md/t/creating-properties-that-are-a-tag-type/63922
- YAML pitfalls to respect on export: spaces-not-tabs indentation, quote values containing colons; internal `[[links]]` inside Text/List values get quoted. Source: https://obsidianmate.com/article/obsidian-properties-complete-guide

## 3. Recommended sync direction/scope for first slice

**Two one-way flows, no write-back into the vault (no bidirectional sync yet):**
1. **Vault → Open Notebook (ingest, read-only):** bind-mount vault `:ro`, `inotifywait`/watcher on an ingest folder posts new/changed `.md` to `POST /sources` (`sources.py:698`). Skip `.obsidian/` entirely. This delivers `local-open-notebook.md` Tasks 4–5 with zero conflict surface.
2. **Open Notebook → export folder (not into the vault):** serialize `Note` (`notes.py`, `notebook.py:712`) to `./notebook_export/<slug>.md` with YAML frontmatter (`title`, `note_type`, `notebook_id`, `updated`, `tags: [open-notebook]`), body = content verbatim; optionally append an `obsidian://open?vault=…&file=…` deep-link line (Option B) so users jump from export to vault manually.
- Explicitly out of scope for slice 1: writing into the vault, delete propagation, rename tracking, attachment copying, `.obsidian` access, plugin dependency. Each is a separate decision with conflict implications below.

## 4. Conflict policy options (for when write-back is proposed)

| Policy | How it behaves on concurrent vault↔app edits | Existing-tool precedent | Fit for notes |
|---|---|---|---|
| **A. Export-only / read-only vault (recommend now)** | No conflicts possible: app never writes paths the vault owns. | `local-open-notebook.md` Tasks 4–5 as specified. | Best first slice. |
| **B. Last-write-wins (mtime/`updated`)** | Later timestamp silently overwrites earlier; simple, lossy. | Generic file sync default; warned against for important vaults: https://synch.run/blog/obsidian-sync-conflicts ("don't rely on latest-file-wins without recovery"). | Acceptable only with version history/audit log. |
| **C. Auto-merge (diff-match-patch) + version history + optional conflict files** | Attempt textual merge; on divergence keep one side, preserve other in history or `Name (ConflictFile-<date>-<device>).md`. | Official Obsidian Sync: "we have chosen merge and use sync history" (https://forum.obsidian.md/t/robust-sync-conflict-resolution/93544); conflict-file proposal https://forum.obsidian.md/t/option-to-let-user-manually-resolve-sync-conflicts/94468; duplication bug history https://forum.obsidian.md/t/obsidian-sync-incorrectly-duplicates-sections-of-files/94732?page=4. REST plugin offers `ifMatch` version for OCC instead of blind overwrite (Option C README). | Right default if/when write-back lands. |
| **D. Manual merge (ours/theirs/open-diff)** | Surface both versions, user picks per file; `git merge --strategy-option ours/theirs` equivalent. | `obsidian-git` conflict-handling feature request (https://github.com/Vinzent03/obsidian-git/issues/803); git-driver example for structured sidecars (https://blog.charlesdesneuf.com/articles/solving-obsidian-readwise-merge-conflicts-with-a-custom-git-driver). | Good for vaults already in git; heavy UX for casual users. |
| **E. CRDT (operation-based merge)** | Concurrent edits to different parts merge automatically by construction. | Theory/practice contrast vs LWW: https://dzone.com/articles/conflict-resolution-using-last-write-wins-vs-crdts | Overkill for file-level note sync; consider only for block-level collaborative editing, not slice 1. |

**Recommendation:** ship A now; design export frontmatter (Section 3) so a future C is additive: stable file names (note id slug), `updated` timestamps, and optional `ifMatch`-style guard if the REST plugin route (Option C) is adopted later. Never sync `.obsidian/` (app code/secrets — the REST plugin blocks it by default; same reasoning applies to filesystem sync).
